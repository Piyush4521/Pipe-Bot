## 2. Cross-Dialect Primary-Key and Integer ID Strategy

### 2.1 The SQLite Rowid Auto-Increment Challenge
In SQLite, auto-incrementing integer surrogate keys require an exact `INTEGER PRIMARY KEY` column definition. Using `BIGINT PRIMARY KEY` in SQLite DDL does not alias the internal 64-bit rowid, resulting in unexpected insert behavior when primary keys are omitted.

Conversely, in PostgreSQL 16, standard auto-incrementing 64-bit keys require `BIGSERIAL` or `BIGINT GENERATED BY DEFAULT AS IDENTITY`.

### 2.2 Reconciled Solution: `BigIntId`
To achieve 100% compatibility across both engines without maintaining separate model hierarchies, a cross-dialect helper was introduced in `backend/app/db/base.py`:
```python
def get_bigint_id_type():
    """Returns a cross-engine compatible integer ID type.

    Compiles to INTEGER on SQLite to alias 64-bit rowid auto-increment.
    Compiles to BIGINT on PostgreSQL (BIGSERIAL for primary keys).
    """
    return BigInteger().with_variant(Integer, "sqlite")

BigIntId = get_bigint_id_type()
```

### 2.3 Verified DDL Output
- **SQLite Compilation**:
  `CREATE TABLE encoder_samples ( id INTEGER NOT NULL, inspection_id INTEGER NOT NULL, ... PRIMARY KEY (id), FOREIGN KEY(inspection_id) REFERENCES inspections (id) )`
- **PostgreSQL Compilation**:
  `CREATE TABLE encoder_samples ( id BIGSERIAL NOT NULL, inspection_id BIGINT NOT NULL, ... PRIMARY KEY (id), FOREIGN KEY(inspection_id) REFERENCES inspections (id) )`

This guarantees that SQLite creates true rowid auto-increment columns, while PostgreSQL provisions high-capacity 64-bit `BIGINT` sequences.

The domain models are implemented across 10 modular Python files in `backend/app/models/`:

| Module | Defined Classes | Key Responsibilities |
|---|---|---|
| `app.models.inspection` | `Inspection`, `InspectionStatus` | Master conduit run entity, pipe geometry, status state machine, archival flag, relationships to events, summaries, telemetry, reports. |
| `app.models.defect` | `Defect`, `DefectClass`, `DefectReviewStatus` | Target conduit anomalies (`Deformation`, `Misalignment`, `Obstacle`, `Rupture`), bounding boxes, review states, model provenance. |

## 4. Alembic Migration Implementation

A new revision was created in `backend/migrations/versions/`:
- **Revision ID**: `e7f8a9b0c1d2`
- **Down Revision**: `d4d255efae0c`
- **Title**: `add_telemetry_devices_and_domain_tables`

### 4.1 Migration Characteristics
1. **Additive and Non-Destructive**: All existing tables (`inspections`, `defects`) and rows are preserved.
2. **Batch Alteration on SQLite**: Altering `defects` to add `model_version_id` executes through `op.batch_alter_table` to navigate SQLite table copy requirements safely.
3. **Topological Creation Order**: Tables are created in strict dependency order (`devices` -> `ai_model_versions` -> `device_sessions` -> `device_heartbeats` -> `vehicle_status_events` -> `encoder_samples` -> `imu_samples` -> `camera_frames` -> `evidence_media` -> `localization_records` -> `inspection_events` -> `inspection_summaries` -> `inspection_reports` -> `audit_events`).
4. **Reversible Downgrade Path**: The downgrade function drops all newly created objects in reverse topological order, restoring the schema precisely to revision `d4d255efae0c`.

## 5. Architectural Deferrals and Refinements

Based on Stage 3 engineering review requirements, several conceptual features from earlier stages were deliberately refined:

### 5.1 Unpartitioned Telemetry Tables
- *Decision*: In Stage 3, `encoder_samples`, `imu_samples`, and `camera_frames` are created as standard, unpartitioned relational tables.
- *Rationale*: PostgreSQL declarative table partitioning introduces schema dialect discrepancies that are invalid in SQLite. Unpartitioned tables provide 100% identical behavior across SQLite development environments and PostgreSQL test instances.
- *Future Upgrade*: When telemetry volumes exceed 1,000,000 rows and benchmark evidence demonstrates write-amplification or query degradation, declarative time-based partitioning (`PARTITION BY RANGE (recorded_at)`) will be introduced via a dedicated PostgreSQL migration.

### 5.2 Deferral of BRIN Indexes
- *Decision*: Block Range Indexes (BRIN) were excluded from cross-database migration DDL.
- *Rationale*: BRIN is a PostgreSQL-specific indexing method that causes syntax errors in SQLite. Standard composite B-tree indexes are used instead.
- *Future Upgrade*: BRIN indexes on `recorded_at` will be added in a PostgreSQL-specific post-migration script after live data volumes justify block-range skipping.

### 5.3 Sensor Data Nullability
- *Decision*: Raw sensor readings (`left_ticks`, `right_ticks`, `accel_x`, `accel_y`, `accel_z`, `gyro_x`, `gyro_y`, `gyro_z`) are mandatory non-null columns. Derived metrics (`left_rpm`, `right_rpm`, `speed_mps`, `pitch_deg`, `roll_deg`, `yaw_deg`) are strictly nullable.
- *Rationale*: Physical crawler firmware contracts remain in development. Assuming calibrated angular rates or RPM during raw sensor ingestion would induce calculation errors.
